BAR: A Backward Reasoning based Agent for Complex Minecraft Tasks

2026-11-13

主要贡献：把复杂任务的规划从「从初始状态正向推理下一步」重构为「从终态（目标已达成）逆向递归分解目标」，绕开初始状态与任务目标之间的巨大感知差距（perception gap）。BAR 由三个模块构成：递归目标分解（recursive goal decomposition）、状态一致性维护（state consistency maintenance）、阶段记忆（stage memory），分别对应稳健、一致、高效三条规划性质。 创新点：① 用「一个 step + 若干 sub-goals」的多轮递归分解替代一次性分解，分解结果以自然语言存在、不依赖预定义 step 集；② 用 step scoring / sliding window 选锚点 + 正向推理补全，融合正逆向推理消除跨步骤状态冲突；③ 用阶段记忆复用高成功率的目标分解结果。以 GPT-4 为骨干在 Minecraft 科技树 53 任务上，静态规划 stone 组 Accuracy 达 87.91（比 Chain-of-thought 的 75.82 高 12.09 个百分点），动态规划再提到 92.31。

研究动机

问题

LLM agent 要完成一个复杂任务，不可能一步到位，关键在「如何把任务分解成可执行的步骤」。现有 LLM 规划方法几乎都在做 forward reasoning——从 agent 的初始状态（一步都还没执行）出发，推断下一步该做什么。这种范式在复杂任务上会失效：以开放世界环境 Minecraft 里的复杂任务「获得 1 把钻石镐（obtain 1 diamond pickaxe）」为例，正向推理的 agent 在走到「Craft 8 stick（制作 8 根木棍）」这一步之后，就再也推不出正确的下一步了。

失效的根因是感知差距（perception gap）：agent 的初始状态和任务目标之间隔着很长的中间步骤，每一步都有一大堆候选动作可选，越往后候选空间越大，LLM 要在远离目标的候选里挑出正确的一步，本身就违背它的强项。

这个感知差距随任务变长会非线性放大：从初始状态正推时，每推一步都要在「当前物品能合成的所有东西」里选下一个，第 k 步的正确选择依赖前 k-1 步的累积状态，任何一个中间步骤推偏，后续所有步骤都跟着偏；而「离目标越远的步骤」其候选与目标的关联越弱，LLM 的强项（从明确前提出发做短链推理）被稀释成「在庞杂候选里猜」。这就是为什么 CoT 类方法在短任务上尚可、在长计划任务（如 gold 组均长 16.86）上显著退化——任务越长，正向推理要「一步不错地穿过」的候选森林越深。

这类失效的代价不是「benchmark 分数低一点」，而是规划任务在真实部署里根本跑不通——一旦某一步推错，后续所有步骤都建立在错误前提上，整个 plan 报废。反向推理（backward reasoning）之所以被本文选中，正是因为它从「目标已达成」的终态出发，天然消除了这个长距离：终态已经拥有钻石镐，最后一步必然是「Craft 1 diamond pickaxe」，倒数第二步必然是准备它的材料「Mine 3 diamond」，如此倒推，每一步的候选都被前一步严格约束。

选择 Minecraft 作为平台有三个实际理由（附录 A）：其一，它自由度高、任务丰富，能模拟大量贴近真实世界的场景与任务（采集材料、合成工具），探索 agent 在其中的行为对真实应用有直接借鉴意义；其二，它的任务类型足够多样、且复杂到能真正挑战 agent 的规划能力；其三，仿真环境完全可控，便于开展大规模可重复的科学实验。这三点分别对应「代表性」「难度」「可控性」，缺一不可。

但逆向推理也不是银弹，它有自己的一套盲区（图 2）：agent 只盯着「当前要达成的目标」，忽略了「当前所处的世界状态」。例如在插入「Craft 1 wooden pickaxe」之后，逆向推理立刻推出「Mine stone」，但 stone 只能在地底获得、而 agent 此刻还在地面，这一步物理上无法执行，最终规划失败。这暴露出纯逆向推理的固有缺陷——它对「执行每一步前后自身的物理状态」是盲的。因此，「从终态倒推」只是必要不充分条件：要真正落地，还必须补上「状态一致性」这一环，这正是 BAR 三个模块各司其职的来源。

笔者注：backward reasoning 在 LLM 社区之外有很长的历史，可追溯到 Newell 等人在 General Problem Solver（GPS）里提出的「子目标归约原则」（principle of subgoal reduction），此后「regression planning」（回归规划）成为符号规划社区的研究主线（McDermott, 1991）。本文的递归目标分解是这条路线在 LLM 时代的自然语言重述。

现有范式

现有工作把规划当作「从初始状态正向展开」的问题，大致有三条路线：

  • 正向逐步推理（iterative forward reasoning）：CoT（Wei et al. 2022）、Plan-and-Solve（ACL 2023）、Tree-of-thought（NeurIPS 2024）等，从初始状态逐步推断下一步；局限在于感知差距，任务越长推得越偏。
  • 从预定义 step 集里选（selection from pre-defined steps）：Selection-Inference（2022）、Faithful Reasoning（2022）、DEPS（NeurIPS 2023）等，从候选步骤集中挑最优组成 plan；局限在于受制于预定义集合、针对特定任务定制，泛化能力差。
  • 从后往前规划的初步尝试：Optimus-1（2024）、Plan4MC（BAAI 2023）、Voyager（2023）等。其中 Voyager 靠与环境的大量交互逐步拼出正确 plan，Optimus-1 靠迭代交互积累历史经验、再从事知识图谱里检索 plan；局限在于都需要大量试错才能积累足够的检索知识，无法「零交互」直接给出 plan。2.2 节针对 Minecraft 的 agent 工作（Voyager、Jarvis-1、Ghost in the Minecraft）也印证了同一问题——要么依赖环境大量交互，要么依赖预设计的能力库，训练出的模型与特定任务高度耦合、无法泛化。

现有方法的三个决定性限制：

  1. 规划都从初始状态出发，受制于初始状态与目标之间的感知差距，任务越长候选越多、越容易推错；
  2. 要么依赖预定义 step 集或针对特定任务定制，无法泛化到任意任务；
  3. 已有 backward 尝试需要大量试错与历史经验积累，无法「零交互」直接规划。

作者提出的问题：能否让 agent 从终态出发、在不依赖预定义步骤集、也不需预先与环境试错的前提下，对任意复杂任务直接做出稳健且一致的规划？

这个新范式的实质，是把三条性质分别替换掉：信息起点从「初始状态」换成「终态（目标已达成）」；分解方式从「一次性分解」换成「多轮递归分解（一个 step + 若干 sub-goals）」；规划依赖从「预定义步骤集 / 历史试错」换成「自然语言分解 + 可选的环境交互记忆」。差别不在模型大小，而在推理的方向与分解的组织方式。

这个范式要成立，依赖两个前提：其一，LLM 能从「目标已达成」倒推「达成它的最后一步」，这一步的候选远比正向少；其二，任务目标能被递归地拆成子目标，直到每个子目标对应一个可直接执行的 step。两个前提分别对应「逆向候选收敛」与「目标可递归」这两个任务结构特征——前者由 Minecraft 合成树的收敛性保证，后者由「每个物品都可递归追溯到基础原料」保证。缺了前者，逆向推理与正向推理一样面临候选爆炸；缺了后者，递归分解无法终止。而「消除状态冲突」这一目标，则额外依赖第三个前提——LLM 具备在短距离内做正向推理、追踪自身位置与库存变化的能力，这正是模块 (b) 能成立的条件。

笔者注：为什么「从终态倒推」比「从初始状态正推」更可靠？因为 Minecraft 的合成树（technology tree）是收敛的——每个物品的合成配方唯一或几乎唯一，从成品倒推材料几乎没有歧义；而从初始状态正推，一个 log 可以合成 planks、stick、crafting_table 等多种东西，分支爆炸。这就是「感知差距」在任务结构上的具体来源。

方法

BAR 由三个模块组成：(a) 递归目标分解负责从终态生成稳健的初始 plan；(b) 状态一致性维护负责消除跨步骤的状态冲突；(c) 阶段记忆负责利用环境交互进一步提升效率。前两个模块提供稳健与一致的规划，第三个模块在「与环境的交互」上做文章。三个模块按顺序串联：先 (a) 出初始 plan，再 (b) 修状态冲突，最后 (c) 在执行反馈中积累记忆以服务后续任务。

问题建模与数据结构

本文没有给出紧凑的数学元组，规划被描述为一个「目标 → 步骤序列」的映射，其核心数据结构是两个容器：Step Stack（步骤栈，存最终 plan 的步骤）与 Goal Queue（目标队列，存待分解的目标）。递归分解的完整流程见算法 1：

##### 算法 1 Recursive Goal Decomposition（附录无编号，正文 §3.1）

Input: Task goal G Initialization: goal_queue GQ = [G], step_stack SS = [], plan P = [] repeat top_goal \leftarrow GQ.get_top_goal() decomposed_step, sub_goals \leftarrow Decompose(top_goal) SS.push(decomposed_step) for i in range (len(sub_goals)) do GQ.push(sub_goals[i]) end for until GQ is empty repeat top_step \leftarrow SS.pop() P.append(top_step) until SS is empty Output: P

  • \boldsymbol{G}：任务目标，如「obtain 1 diamond pickaxe」；
  • \boldsymbol{GQ}：目标队列，先进先出，初始只含 G；
  • \boldsymbol{SS}：步骤栈，后进先出，存已分解出的 step；
  • \boldsymbol{P}：最终 plan，由 SS 依次弹出得到；
  • \boldsymbol{Decompose(\cdot)}：把单个 goal 拆成一个 step 与若干 sub-goals 的 LLM 调用。

算法的关键在「先压栈、后弹栈」的次序：分解时越早拆出的 step（越靠近终态）越先入栈、越晚弹出，于是 P 的顺序恰好是从初始状态到终态的正序。这个次序转换把「从终态倒推」翻译成了「从初始状态正序执行」的可执行 plan，是递归分解与逆向推理之间的连接点。

这两个容器不是随意选的：Step Stack 用后进先出（LIFO），因为分解是「从终态向初始状态」进行的，先拆出的 step 离终态近、后拆出的离初始状态近，只有栈的逆序弹出才能把「倒推顺序」翻转成「正序执行」；Goal Queue 用先进先出（FIFO），因为子目标之间通常有「先备材料、后合成」的偏序，按队列的广度优先顺序逐个分解，能保证每个子目标在轮到它时，其依赖的更底层子目标已被安排进队列。如果把 Goal Queue 换成栈（深度优先），会先钻进某个子目标的深层依赖，打乱材料准备与合成的先后关系。

递归目标分解（recursive goal decomposition）

单次迭代就把一个复杂任务拆成全部步骤是极难的，尤其是长计划任务。原因有二：一是候选爆炸——从初始状态正推，每一步有大量可选动作，一次性把整条链推完要求 LLM 在所有交叉分支里一次性选中唯一正确的路径，搜索空间随步数指数增长；二是长程依赖——第 N 步的正确与否取决于前 N-1 步的累积状态，单次生成没有机会在中间修正。受动态规划（Bellman, 1954）启发——每轮迭代的当前问题解由「立即可得的结果」+「留给后续迭代继续求解的剩余结果」两部分构成——本文让每轮分解把目标拆成一个 step（立即可执行）和若干 sub-goals（还需进一步分解），sub-goals 作为 task goal 与最终 plan 之间的过渡。

以「obtain 1 diamond pickaxe」为例，第一轮把 goal 拆成：一个 step「Craft 1 diamond pickaxe」+ 三个 sub-goals「Collect 3 diamond」「Obtain 2 stick」「Obtain 1 crafting_table」。分解出的 step 压入 Step Stack，sub-goals 依次入 Goal Queue；下一轮从 Goal Queue 队头取新目标重复分解，直到队列清空。最后从 Step Stack 依次弹栈得到最终 plan。由于可能产生多个同类 step，需按物品数量相加融合，例如「Obtain 3 stick」+「Obtain 2 stick」融合成「Obtain 5 stick」。

每一轮分解的「输入 → 操作 → 输出」可以精确描述为：输入是 Goal Queue 队头的一个目标；操作是调用 LLM，用附录 C 的 goal decomposition prompt 把它拆开；输出是一个 step（压入 Step Stack）与若干 sub-goals（依次入 Goal Queue）。终止条件是 Goal Queue 为空——此时所有子目标都已递归地落成 step，plan 的骨架完整。这个递归结构保证了一个性质：任何一个 sub-goal 都不会被「悬空」，它最终要么自身就是一个可直接执行的 step，要么被继续拆成更细的 step，直到全部落到可执行层。

存疑：论文未说明递归分解的循环保护——如果 LLM 把某个 goal 错误地分解成它自己（如「obtain 1 iron pickaxe」的 sub-goal 里又出现「obtain 1 iron pickaxe」），Goal Queue 永远不会清空，算法 1 会陷入死循环。这在 LLM 生成不稳定时是现实风险，但全文均未给出「最大迭代次数」或「子目标不得等于父目标」这类终止兜底，复现时需自行加保护。

这个模块的价值有三点：分解从终态出发，规避了感知差距；多轮递归把「一次性分解长计划」的难度摊薄为「每轮只拆一个 step」；分解产物是自然语言的 step 与 sub-goal，不依赖外部预定义步骤集或任务定制，因此能处理任意任务。

同类 step 的融合（「Obtain 3 stick」+「Obtain 2 stick」→「Obtain 5 stick」）不是可有可无的后处理，而是保证 plan 可执行的必要步骤：递归分解会从不同子目标各自推出「获得木棍」这类重复需求，若不合并，最终 plan 会出现两次「Craft stick」，第二次执行时材料已耗尽、导致执行失败。合并的依据是「同类型 step 的物品数量相加」，这要求 step 的表示能解析出「动作动词 + 物品 + 数量」三元组，是自然语言 step 能被程序化融合的前提。

这里有一个刻意为之的选择：分解产物用自然语言而非形式化算子。符号规划社区的 regression planning 之所以能成立，靠的是「动作有形式化的前置条件与效果」这一强假设；而 Minecraft 里物品配方、位置前提（如「stone 只在地底」）这些知识散落在 LLM 的预训练参数里，用自然语言表达才能让 LLM 直接调用这些隐含知识，不必人工为每类动作写前置/效果规则。代价是自然语言 step 需要额外的融合与校验（模块 b 正是为此而生），但换来的是对「任意任务」的免定制覆盖。

##### 附录 C goal decomposition 的 prompt（附录 C.1）

System: You are a helpful assistant in Minecraft. I will give you a goal to achieve in Minecraft, and you need to decompose the goal into a single step and a list of sub goals to achieve. Output the reasoning thought and the decomposed result. You can follow the history dialogue to make the decomposition.

User: ======== Goal: collect 3 stone. Thought: To collect 3 stone, the last step is to mine 3 stone with wooden_pickaxe, as mining the stone requires at least wooden_pickaxe. And the previous sub goals are to obtain 1 wooden_pickaxe and dig down with wooden_pickaxe, because stone only appears at the below ground level. Based on these analysis, the decomposed result is as follows: Decomposed Step: Mine 3 stone with wooden_pickaxe Decomposed Sub Goals:

  1. Obtain 1 wooden_pickaxe
  2. Dig down with wooden_pickaxe ========

======== Goal: {new goal} Thought:

Assistant:

笔者注：为保证与基线公平对比，本文只提供目标物品的配方信息（recipe），不提供中间 sub-goals——这正是「倒推」得以成立的充分条件：给出配方，LLM 就能从成品倒推材料。

这个 prompt 的 few-shot 示例（「collect 3 stone」→ 拆成 step「Mine 3 stone with wooden_pickaxe」+ 子目标「Obtain 1 wooden_pickaxe」「Dig down with wooden_pickaxe」）起的是「示范输出格式 + 示范倒推思路」双重作用：它既告诉 LLM 输出要分「Decomposed Step」与「Decomposed Sub Goals」两栏，又示范了「先想最后一步、再想它的前置」的推理顺序。值得注意的是示例里把「dig down」也列成了 sub-goal 而非 step——这暗示「下挖」在某些语境下被视为一个需继续分解的目标，体现了「step 与 sub-goal 的边界由 LLM 按语义灵活判断」这一设计弹性，而非预先硬编码的动词分类表。

状态一致性维护（state consistency maintenance）

递归分解虽绕开了感知差距，但仍有缺陷：agent 只盯着「当前要达成的目标」，忽略了「当前世界状态」。如图 2 所示，agent 在插入「Craft 1 wooden pickaxe」后立即推出「Mine stone」，但 stone 只能在地底获得，而 agent 此刻还在地面，这一步无法执行，最终导致规划失败。逆向推理对「执行每一步前后自身的物理状态」是盲的，而正向推理恰好对此敏感——因此本文把两者融合。

流程是：由模块 (a) 生成初始 plan 后，从中选一对「start / end anchor steps」，两锚点之间最可能因状态冲突生成错误；然后用正向推理生成两锚点之间的 partial plan；最后把初始 plan 与 partial plan 融合，修正初始 plan 的错误。选锚点有两种方法：

  • step scoring（步骤打分）：把初始 plan 的每个 step 按 1–10 打分，1 表示「从这一步起的接下来几步很可能错」，10 表示「完全准确」；评分低于阈值 t 的 step 选作 start anchor，其后的第 k 个 step 选作 end anchor。
  • sliding window（滑动窗口）：从初始 plan 中随机选 start / end anchor，间隔固定 k 步。

两种方法的差别在「锚点是否由质量信号驱动」：step scoring 先让 LLM 对每个 step 打一个「可靠性」分、再挑出低分区补全，属于「有的放矢」；sliding window 则完全随机取锚点、不区分区间好坏，属于「无差别扫射」。滑动窗口存在的意义在于提供一个「不依赖额外 LLM 打分调用」的廉价基线——它省掉了一次全 plan 的打分开销，但代价是可能对「本来就对」的区间做无谓补全。这一对照在消融里被用来论证「打分这一步的调用是值得的」。

以「obtain 1 diamond pickaxe」为例，step scoring 发现「Craft 1 crafting_table」这一 step 评分低于阈值，于是选它作 start anchor，其后的第 k 步「Craft 1 furnace」作 end anchor，正向推理生成二者之间的 partial plan。融合后 agent 发现初始 plan 漏了关键一步：在 mine stone 之前应当先向下挖（dig down）到达地底。于是补上缺失步骤，得到 refined plan。

  • \boldsymbol{t}：step scoring 的评分阈值，正文设定为 5（附录 B 无此值，见实验设置）；
  • \boldsymbol{k}：end anchor 相对 start anchor 的偏移步数，正文设定为 3。

参数 k 的取值还有一个隐含约束：它控制 partial plan 的长度要远小于初始 plan 的长度。原文在注释里点明这一动机——正向推理在长 plan 上表现差，所以「锚点间补全」必须只补一小段，而不是让正向推理去补一条长链。k=3 意味着每个 partial plan 最多补 3 步，把正向推理的作用域限制在它擅长的短距离上。

阈值 t=5 的语义也值得说明：评分是 1–10 分，t=5 意味着「评分低于 5（即 LLM 认为从这步起接下来几步很可能错）」的 step 才被选作 start anchor。5 恰好是「中位偏保守」的阈值——如果设得太低（如 3），只有「几乎肯定错」的 step 才触发补全，会漏掉「半信半疑」的可疑区间；设得太高（如 8），则几乎所有 step 都触发补全，退化成「全量正向重推」，既慢又引入噪声。t=5、k=3 的组合在消融中被验证为较优，但论文未给出这两个值的完整网格搜索结果。

这个模块强制 agent 理解「执行每一步前后的物理状态」，从而消除跨步骤的状态冲突。它与递归分解的分工是：递归分解保证「从终态倒推」不迷路，状态一致性保证「倒推出的步骤在物理上可执行」。

状态冲突的根源可以归纳为逆向推理的一种系统性盲区：逆向推理每一步只回答「要达成 X，需要先做什么」，却不知道「当前 agent 在哪里、手里有什么」。而 Minecraft 里大量步骤带有隐式的位置前提——mine stone 要求在地底、craft 要求手持工作台、smelt 要求手持熔炉——这些前提在「从成品倒推材料」的视角下是看不见的。状态一致性模块正是用「正向推理补局部」来补这个盲区：正向推理从 start anchor 的确定状态出发，逐步骤追踪位置与库存的变化，自然能发现「这一步该先 dig down」这类被逆向推理忽略的前提。

锚点补全的完整操作可拆成四步：打分/选锚点（step scoring 打分选低分区，或 sliding window 随机取）→ 正向补全（用附录 C.3 的 complement prompt，从 start anchor 的正向状态出发生成到 end anchor 的 partial plan）→ 融合修正（用附录 C.4 的 integrate prompt，对比初始 plan 与 partial plan，指出遗漏并输出 corrected plan）→ 替换（用 corrected plan 覆盖初始 plan 对应区间）。这套「打分—补全—融合」的三段式，本质是把「状态冲突检测」从「写死规则」变成了「让 LLM 在短距离正向推理中自己发现」，这也是它能覆盖任意任务、而不只是「stone 在地底」这类已知规则的原因。

阶段记忆（stage memory）

除了利用 LLM 的推理能力，环境交互还能进一步提升效率。现有工作（Voyager、Jarvis-1、AgentSims）记录的是整个 plan 的执行结果，而整个 plan 对「目标不同的新任务」不适用，记忆利用率低。

本文的解法是把记忆的粒度降到「单个目标的一次分解」。因为 agent 是分多轮分解目标，每一轮的分解结果都能复用于新任务里相同目标的分解。为了筛出准确的分解结果，先把 (a)(b) 生成的 plan 拿到环境里执行，执行成功率越高，对应 plan 的分解结果越准确。执行后记录每个 plan 的执行成功率与规划过程中的目标分解结果，称为 stage memory。新任务规划时，从 stage memory 里检索「相同 goal 且执行成功率高」的分解结果，辅助新任务里该目标的分解。

例如，执行过「obtain 1 fence」「collect 1 gold ingot」等任务的 plan 后，把它们的分解结果与成功率存入 stage memory；当规划新任务「collect 1 redstone」时，就能检索到相同 goal「obtain 1 iron pickaxe」的分解结果辅助分解。于是 agent 靠 stage memory 持续提升目标分解的效率。

stage memory 的每条记录至少包含三个字段：目标（goal）——检索的主键，用于跨任务匹配相同的分解需求；该目标的分解结果（一个 step + 若干 sub-goals）——被复用的有效载荷；所属 plan 的执行成功率——质量信号，用于过滤掉那些「分解看似对、执行却失败」的坏样本。检索时按 goal 匹配、再按成功率排序取高者，正文设定的筛选阈值是成功率 \geqslant 0.3（见实验设置）。

写入与检索的时机也有讲究：stage memory 只在执行完 plan 之后写入（因为成功率要等执行结果出来才能算），只在规划新任务、遇到相同 goal 时检索。这保证了记忆里存的是「被环境验证过的分解」，而不是 LLM 未经验证的猜测——这是它与「直接把历史对话当上下文」这类朴素记忆的关键差别：后者存的是未经验证的输出，错一次就会污染后续所有任务。

存疑：论文只说「检索相同 goal 的分解结果」，但没说明「相同」的判定口径——是 goal 字符串的精确匹配（如「obtain 1 iron pickaxe」必须逐字相同），还是允许语义等价（如「obtain 1 iron pickaxe」≈「get 1 iron pickaxe」）。从图 3(c) 的示例看是同一物品的同型 goal 匹配，但若严格精确匹配，stage memory 的复用面会很窄；若语义匹配，则需要额外的嵌入或规则。这个口径直接决定 stage memory 的召回率，是复现时的关键未知项。

笔者注：stage memory 与「整段 plan 记忆」的本质差别在复用粒度——前者以「目标」为单位、可跨任务拼接，后者以「完整计划」为单位、只能整段套用。这决定了 stage memory 能随任务库增长持续受益，而整段记忆会随新任务目标漂移而迅速失效。

三模块协同的整体流程

三个模块不是三个独立组件，而是一条按需激活的流水线。静态规划（无环境交互）只用到 (a)(b)：任务目标先进模块 (a)，经递归分解得到初始 plan；初始 plan 再进模块 (b)，经锚点补全消除状态冲突，输出 refined plan 即为最终结果。动态规划在此基础上追加 (c)：把 (a)(b) 生成的 plan 拿到环境里执行、记录成功率与分解结果入 stage memory；随后对同一批任务重新规划，这次模块 (a) 在分解每个 goal 时都会先查 stage memory，用高成功率的同类分解结果辅助，从而在不改变 (a)(b) 逻辑的前提下提升分解效率。

这条流水线的一个设计要点是「模块解耦」：stage memory 只在 (a) 的分解环节做「检索增强」，完全不碰 (b) 的状态一致性。这保证 stage memory 的收益是可叠加的——即便将来 (a) 或 (b) 被替换成更强的分解/校验方法，stage memory 的检索增强依然适用。这与许多把「记忆」和「规划」耦合成一个黑箱的做法形成对照。

从 LLM 调用开销看，三个模块的调用量是逐级叠加的：模块 (a) 每拆一个 goal 调一次 LLM，总调用次数约等于「goal 分解的总轮数」，与 plan 长度同阶；模块 (b) 在 (a) 之后额外加「一次全 plan 打分 + 每个锚点一次补全 + 每次补全一次融合」，用 step scoring 时至少多 1 + 2·|锚点数| 次调用，用 sliding window 则省去打分那一次；模块 (c) 的动态规划还要先把 plan 执行 10 次、再对每个 goal 做一次带记忆检索的分解。因此「动态规划」的总成本显著高于「静态规划」，其收益是「一次交互换来 plan 质量跃升」——这也是论文把静态、动态分开评测、而不是只报动态数字的原因：静态规划度量的是「纯推理能力」，动态规划度量的是「推理 + 交互」的上限。

步骤封装与环境（附录 B.3 回填）

动态规划实验需要在 Minecraft 里真正执行 plan，但低层键鼠操作（精确选择合成格、拖动物品）当前的低层控制器不可靠。因此本文基于 Jarvis-1 的做法，把细粒度键鼠操作封装成三类高频 step——craft（合成）、smelt（熔炼）、equip（装备），用启发式规则保证这三类动作能按预期完成；另两类重要 step mine（挖掘）与 dig down（下挖）则用 SOTA 低层控制器 MineDreamer 直接执行自然语言指令。

动作空间是 11 种键鼠原语，封装把其中「合成/熔炼/装备」收成可由启发式规则可靠执行的复合动作，而挖掘/下挖交给 MineDreamer 这种用「当前帧 + 文本指令」生成下一帧来引导 agent 的低层模型。

##### 附录 B.3.2 环境设置

为保证公平比较并排除环境无关因素的干扰，做了两类初始化：

  • 全局环境初始化：agent 每次出生在固定场景的固定位置、空背包（从固定初始状态开始执行）；暗处仍保持明亮视野（地底执行不受黑暗影响）；环境设为和平模式（无僵尸等生物干扰）；环境恒为白昼。
  • 矿石分布初始化：在地底预置矿石，命令为 ⁠/fill <from_x> <from_y> <from_z> <to_x> <to_y> <to_z> minecraft:ore；具体实现了一个矿石分布算法，在 agent 出生点周围的地底生成多层同心方环矿石，保证「只要 plan 正确，就能挖到足够矿石」。

笔者注：矿石分布初始化的动机值得注意——它把「执行成功率」这个指标与「规划质量」解耦：如果不预置矿石，执行失败可能来自「矿石稀缺」而非「plan 错」，会污染 stage memory 里「成功率 ≈ 分解准确性」的假设。

Reverse Chain（D.1，最能体现 backward 基线）： System: You are a helpful assistant in Minecraft. I will give you a goal to achieve in Minecraft, and you need to decompose the goal into a sequence of steps. To collect 3 stone, I need to mine 3 stone with wooden_pickaxe. stone usually exists underground, so I need to dig down with wooden_pickaxe. 笔者注：Reverse Chain 是「一次性倒推到底」——它必须把整条链在脑子里一次推完，这正是本文要改进的点：BAR 用「每轮只拆一个 step + 子目标」的递归，把长链倒推摊薄成多轮短倒推。这一对照是理解 BAR 与朴素 backward 基线差别的关键。

其余基线（Self-Refine、Tree-of-thought、DEPS、Plan-and-Solve、OpenAI-o1、React、Jarvis-1）的完整 prompt 见附录 D，其机制已在结果解读中逐一说明，此处不重复。

  • 指标。 三个基于重叠计算的文本指标（附录 B.2）：
    • Accuracy：生成 plan 的每一步与 ground truth 同索引步骤是否精确匹配；
    • F1-Score：兼顾 precision 与 recall，某一步只有「它与前一步组成的二元对」能在 ground truth 中找到才算生成正确；
    • Edit Distance：把生成 plan 变成 ground truth 所需的最少编辑操作数（替换 / 插入 / 删除单个 step）。

    Acc 与 F1 越大越好、ED 越小越好。执行指标为平均执行成功率与执行耗时（每个任务执行 10 次取平均）。

笔者注：三个指标的分工值得留意——Accuracy 只看「同位置对不对」，对「整体对了但错位」会误判；F1 用相邻二元对部分缓解了错位问题；Edit Distance 对顺序敏感度最低、最贴近「改多少步能修好」。三者互补，单看任何一个都会低估或高估规划质量。

  • 协议。 静态规划只比较模块 (a)(b)，不交互环境；anchor 选取设 t=5、k=3。动态规划先把 (a)(b) 生成的 plan 执行 10 次、记录平均执行成功率入 stage memory，再借助「成功率 \geqslant 0.3 的分解结果」对所有任务重新规划。所有 LLM 温度设为 0（可复现），每任务跑 10 次取平均。

stage memory 的成功率阈值 \geqslant 0.3 是一个偏宽松的过滤：只要一个分解结果在 10 次执行里平均成功 3 次以上就算「可复用」。这个阈值的选择动机是「宁缺毋滥」与「可用性」的折中——设得太高（如 0.8）会让绝大多数分解结果被过滤掉、stage memory 里几乎无记忆可用；设得太低（如 0.1）则会把「基本靠运气成功」的坏分解也纳入检索、污染后续规划。论文未给出该阈值的敏感性分析，是复现时需要自行试探的超参。

静态规划

结论先行：以 GPT-4 为骨干的 BAR 在 5 组 × 3 指标共 15 个格子上全部取得最优（粗体），且以开源 Llama-3-8B 为骨干时仍显著优于同骨干的其他基线。

表 1：静态规划结果。列分组为 stone/iron/diamond/redstone/gold，每组含 Acc↑ / F1↑ / ED↓ 三个指标；粗体为最优、下划线为次优。

按组来看，Ours-GPT4 在 stone 组 Accuracy 达 87.91，比最强的专有基线 GPT4 版 Chain-of-thought 的 75.82 高 12.09 个百分点，Edit Distance 从 2.09 收紧到 1.00；iron 组 Accuracy 82.67、F1 85.02，比 CoT-GPT4 的 77.26 / 78.12 各高约 5.4 / 6.9 个百分点；redstone 组 Accuracy 80.53，比 CoT-GPT4 的 47.66 高 32.87 个百分点——这是差距最大的一组，redstone 任务的计划更长（16.14）、中间步骤更多，正向推理的感知差距被放大到极致；gold 组 Accuracy 85.59、F1 87.34，比次优的 o1（Acc 75.42、F1 83.97）分别高 10.17 / 3.37 个百分点。diamond 组 Accuracy 87.39，比次优的 Reverse Chain-GPT4（86.49）仅高 0.90 个百分点——这是差距最小的一组，说明纯逆向推理在「从成品倒推材料」这一最容易的环节上已接近天花板，BAR 的额外优势主要体现在其他组与状态冲突频发的场景。开源骨干上 Ours-Llama-3-8B 的 stone 组 Accuracy 78.02，比同骨干 Chain-of-thought 的 68.97 高 9.05 个百分点，证明方法对开源模型同样稳健。

三条发现支撑了范式判断：(1) Chain-of-thought 因感知差距而失效，任务越长越糟；(2) Reverse Chain 摆脱了感知差距，但「单纯换方向」解决不了跨步骤状态冲突，性能反而有损（其 GPT4 版 gold 组 Accuracy 仅 52.17，低于 Chain-of-thought 的 52.54）；(3) 精修与探索类方法各有各的失效方式——Self-Refine、DEPS 靠 LLM 自反馈修正，但初始 plan 仍基于正向推理，与 CoT 同病，且多轮精修的误差传播会引入无关噪声、LLM 不稳定的反馈会把推理引向错误方向；Tree-of-thought 探索多条路径，但「用 LLM 评估一个尚未完成的 plan 的质量」本身不可靠，大量候选步骤反而让 plan 混入多余噪声；Plan-and-Solve、o1 靠预览部分 plan、反复推演来改善，但无论如何探索反思，都改变不了「远离任务目标的正确步骤本来就推不出」这一根本缺陷。一句话，这些方法都在「正向推理的框架内打补丁」，而 BAR 换掉了框架本身。

动态规划

表 2：动态规划结果（文本指标）。Ours-static 指仅 (a)(b) 模块 + GPT4 的静态规划，Ours-dynamic 指含 stage memory 的完整 agent + GPT4。

借助 stage memory，Ours-dynamic 在全部 5 组进一步超越静态版本：iron 组 Accuracy 从静态的 82.67 提到 96.58（+13.91 个百分点），stone 组从 87.91 提到 92.31（+4.40）。对比同样是交互式方法的 React（iron 组 Acc 89.17、stone 组 70.33）与 Jarvis-1（stone 组 75.82），stage memory 的「一次交互」就带来显著提升。

执行指标（图 5）给出更贴近真实部署的结论：成功率与耗时是双目标权衡。

Ours-Dynamic 在三组里成功率最高（diamond 39.62%、redstone 44.29%、gold 41.43%），同时耗时反而更低；纯交互的 React 最低（14.29% / 14.29% / 21.43%）。值得注意的是 React+Ours-Static（用 React 框架执行 BAR 的 plan）成功率跃升到 40.00% / 42.86% / 38.57%，接近 Ours-Dynamic——这说明「高质量的初始 plan」才是执行成功的关键，单纯靠环境反馈纠错是低效路径，更好的做法是把力气花在 LLM 生成 plan 的质量上。

动态结果里还有一条容易被忽略的对照：Jarvis-1 的成功率（diamond 10.00%、gold 11.43%）甚至低于纯 React，尽管它「既用 LLM 预训练知识、又用环境游戏经验」。这进一步说明「记忆」若不以「可复用的分解结果」为粒度、而是以「整段 plan 执行记录」为粒度，对目标不同的新任务几乎无效——这正是 stage memory 与 Jarvis-1 记忆机制的分水岭，也是动态规划实验想证明的核心论点。

「一次交互」的效率含义需要量化理解：动态规划比静态规划多出的全部成本，就是「先执行 10 次 + 把成功率入记忆 + 带记忆重规划一轮」，没有任何增量训练、没有强化学习循环。在这个成本下，iron 组 Accuracy 从 82.67 涨到 96.58、涨了 13.91 个百分点，代价仅仅是「跑 10 遍 + 重规划一遍」，对比 Voyager/Jarvis-1 那种「长期在线试错」的交互范式，stage memory 的交互效率高出一个量级。

消融实验

消融验证 state consistency maintaining 模块，并对比两种选锚点方法（step scoring vs sliding window）。如图 6、7 所示，无论 GPT-4 还是 Llama-3 作骨干，该模块都能显著提升 plan 质量——因为「融合正逆向推理」能有效消除跨步骤状态冲突。开源 Llama-3 受益更大，因为它的初始 plan 质量本就低于 GPT-4，可修正的空间更大。

两种选锚点方法中，step scoring 带来更大提升，因为 sliding window 选的锚点对过多、把不必要噪声引入 plan。附录 E.2 的补充消融（Accuracy 与 Edit Distance 指标，图 11–14）得到同样结论：state consistency 模块提升质量、step scoring 优于 sliding window。

消融的机制解读要落在「为什么 step scoring 更好」上：step scoring 让 LLM 先对每个 step 的可靠性打分、只对「评分低于阈值」的区间做正向补全，等于把正向推理的火力集中在最可能出错的地方；sliding window 则无差别地在 plan 上滑动取锚点，无论该区间是否真有问题都去补全，补出来的 partial plan 若本身是对的，就会在融合时引入多余步骤、反而拉低 Edit Distance。这与「正向推理只在短距离可靠、长距离不可靠」的前提一致——step scoring 保证每个补全区间的长度受 k 约束、且落在可疑区间内，sliding window 则两者都不保证。

优势分析（附录 E.1 回填）

为说明 BAR 的优势来源，附录评估了「对 plan 长度的敏感性」与「中间步骤推理的稳定性」。图 9 显示，基线模型性能随 plan 长度增加剧烈波动（尤其长度 7 到 12 区间极不稳定），而 BAR 性能几乎不随长度变化——因为递归目标分解把每次分解的候选空间收窄到「当前一个目标的材料」，分解难度不随 plan 变长而增加。图 10 则评估「中间步骤推理稳定性」：给每个任务提供 ground truth 的部分 plan、让模型补全接下来的三步，每任务采样 50 次、统计这 50 次里出现多少种不同的「三步序列」作为 diversity 值。BAR 的 diversity 始终最低，说明其目标分解与 plan 生成的稳定性最好。

diversity 低之所以是「好」的指标，在于它度量的是「给定相同前缀，模型是否总给出相同的补全」——diversity 低意味着模型对「下一步该做什么」有稳定、确定的知识，而不是在多个候选里随机摇摆。这直接对应规划的可信度：一个 diversity 高的模型，同一任务 50 次能给出十几种补全，说明它自己都不确定正确步骤；BAR 的 diversity 低，说明它的「从目标倒推」把候选压到了几乎唯一，这正是递归分解「收敛候选」这一设计目标在统计上的体现。

存疑：图 9、10 的纵轴与「性能/多样性」的具体数值没有在正文或表格给出，只有趋势描述（「显著波动」「无明显变化」）。若需精确复现这两张图的指标口径（是 F1 还是 Accuracy、diversity 的确切定义与采样协议），需回到代码仓库核对，论文文字层面不可完全复现。

结论

BAR 把复杂任务的规划从「从初始状态正向推理」重构为「从终态递归逆向分解」，用递归目标分解、状态一致性维护、阶段记忆三个模块分别解决感知差距、跨步骤状态冲突、交互效率三个问题。它在 Minecraft 科技树 53 个任务上的静态与动态规划均全面超越现有基线，且长度不敏感、中间步推理稳定，动态规划更证明「高质量初始 plan + 一次交互记忆」优于「低质量 plan + 长期试错」。这一「从后往前递归规划」的范式为 LLM 规划提供了可复用的新起点。

限制

  • 只在 Minecraft 单一环境验证，未在 Web、具身等其他任务环境测试，泛化到不同动作空间与目标结构的能力未知；
  • 动态规划的执行成功率整体偏低（最高 gold 组 44.29%），说明「规划对、执行对」之间仍有较大差距，但论文未拆解失败到底来自规划还是低层控制器；
  • 文本指标基于「唯一 plan + 专家标注」的 ground truth，只适合可枚举的确定性任务，对「多解、可换序」的真实任务会低估模型能力；
  • 评测报告不完整：图 5 的执行指标只覆盖 diamond/redstone/gold 三组（stone/iron 未报告），且全文没有失败案例分析，读者无法判断 BAR 在哪些任务上、以何种方式失败；
  • 关键超参 t=5、k=3 与 stage memory 阈值 \geqslant 0.3 均只给出取值、未做敏感性分析，无法判断这些值离「较优点」有多远、换个值是否显著掉点；
  • 文本指标依赖 3 名专家对 53 个任务逐一标注唯一 ground truth，扩展到更大任务库时标注成本与「唯一 plan」这一约束都会成为瓶颈，方法本身的可扩展评测受制于数据构造难度。
